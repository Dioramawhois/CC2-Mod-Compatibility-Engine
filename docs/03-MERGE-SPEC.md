# 03. Спецификация движка слияния

## 1. Принцип

**3-way merge = BASE + OURS + THEIRS.** Для одного игрового пути `B` берётся из vanilla/Mod SDK той же сборки, `A` и `C` — соответствующие файлы из двух модов. `A` и `C` сравниваются **с B**, а не просто друг с другом. Разные диапазоны изменений обычно объединяются автоматически. Изменение одной и той же строки разными способами — реальный конфликт.

В MVP предполагается использование внешнего `git merge-file` через безопасный subprocess (`shell=False`) и временные файлы:

```bash
git merge-file -p -L MOD_A -L BASE -L MOD_B A.lua B.lua C.lua
```

`-p` пишет в stdout, исходники не модифицируются; exit 0 = бесконфликтное слияние, >0 может означать конфликт или ошибку, различать по документированным правилам Git, не по наличию подстроки `<<<<<<<` в произвольном Lua. При ошибке subprocess ничего не публиковать.

## 2. Decision table

| Вход | Действие MVP | Причина |
|---|---|---|
| Один ресурс на путь | `copy` | Нет файлового конфликта |
| Два/более byte-identical | `deduplicate` | Изменения одинаковы |
| Текст / Lua / constants.txt, база подтверждена | Git three-way | Повторно используем готовую реализацию |
| Текст без достоверной базы | `no_base` | Иначе merge может тихо потерять смысл изменений |
| Два новых разных файла по одному пути | `add_add_conflict` | Общего предка нет |
| Два одинаковых новых файла | `identical` | Совместимы побайтно |
| Delete vs modify | `delete_modify_conflict` | Нельзя сохранять/удалять автоматически |
| XML | Сначала текстовый merge + XML parse; key-based в P1 | Само наличие XML не гарантирует безопасную структуру |
| PNG/FBX/WAV/прочие бинарные | `unsupported_binary` | Нет общей структуры/семантики |
| `.dll` в `content/cc2x/` | `native_plugin_review_required` | Исполняемый код, отдельные правила размещения |
| Неизвестный тип | `needs_review`/`unsupported` | Fail closed |

## 3. Lua

- На MVP Lua обрабатывается как текст, не AST. Результат проходит `luac -p` **версии Lua 5.3**, если доступен валидатор; при отсутствии обязательного валидатора build блокируется в строгом режиме или помечается `needs_review` согласно конфигурации.
- `luac` проверяет **синтаксис**, не типы, игровые API, баланс, мультиплеер, порядок вызовов или логику.
- Сохранять BOM/кодировку и EOL в контролируемой форме, не преобразовывать файлы без необходимости. При конфликтующих кодировках — отдельный `encoding_conflict`.
- Запрет на автоматическое разрешение двумя правками в одной функции лишь потому, что строки не пересеклись: «clean» означает только clean merge; позднее добавить semantic-risk heuristic.
- В P2 — `tree-sitter-lua` для идентификаторов функций, проверок delete/modify, конфликтов одинаковых объявлений, AST parse safety net. Применение `semantic-merge` **требует адаптации под Lua**, его заявленная поддержка Lua отсутствует.

## 4. XML

- В MVP — текстовый merge для well-formed XML, с проверкой парсинга результата. **Не применять автоматическое key-based объединение по произвольному XPath** до описания схемы и устойчивых идентификаторов узлов для CC2.
- В P1 — сделать XML-adapter с node matching по schema-specific ключам, отдельными правилами для атрибутов/детей/порядка, запретом на изменение комментариев/namespace без гарантий. Без надёжного key — fallback в текстовый merge / manual.
- Парсер должен отключать external entities и чтение локальных/сетевых DTD (XXE).
- Порядок элементов может быть семантически значим: нельзя сортировать автоматически.

## 5. N-way, порядок и конфликты

- Все версии одного пути сравниваются с `B` (одним и тем же baseline); для `N>=3` выполняется последовательный 3-way merge, порядок `mod_order` фиксируется в manifest.
- Перед слиянием нужно вычислить парные пересечения изменений относительно B; чистый последний merge не считается доказательством отсутствия скрытых конфликтов.
- Обнаруживать изменение идентичных строк одинаково и конфликт «редактирование против удаления».
- Не использовать «last successful mod wins» и silent override; ручное решение относится к **конкретным хешам входов**.
- Если какой-либо промежуточный merge содержит конфликт, сразу переходить в `conflict`, не продолжать его как будто это валидный исходник.

## 6. Пример на реальном принципе, но вымышленных данных

База (`B`):

```ini
weapon_damage=100
radar_range=5000
vehicle_speed=20
```

Мод A меняет `weapon_damage=150`; мод B меняет `radar_range=8000` — результат обе правки, статус `clean`. **Имена параметров иллюстративны**, а не утверждение об устройстве `constants.txt` игры.

Если A ставит `weapon_damage=150`, а B ставит `weapon_damage=200`, это `conflict` и публикация запрещена без решения.

## Текущее подмножество 0.1.0.dev1

Реализованы byte-identical dedup/copy, парный Git preflight и последовательный accumulator с общей базой. Каждый Git-вызов имеет timeout 10 секунд; exit 1..127 — конфликт, отрицательный или >=128 — ошибка инструмента. Все входы — копии во временном каталоге. `delete_modify_conflict` определяется по диапазонам удаления только после Git conflict; для больших файлов классификация консервативно остаётся `edit_edit_conflict`, сам конфликт не теряется.

Текстовая allowlist: `.lua`, `.txt`, `.xml`; поддержаны обратимые UTF-8 с одинаковым BOM и EOL (LF либо CRLF) у всех участников/базы. UTF-16, NUL, смешанный EOL или несовпадение форматов блокируются. Проверка формата применяется и к copy/dedup. `.dll` в любом каталоге и всё под `cc2x/` блокируется даже при единственном источнике. Уникальные/идентичные известные бинарные ресурсы можно инвентаризировать, разные бинарные версии не сливаются. Неподдерживаемые расширения — `needs_review`.

Нет installable output, сохранённых manual resolutions, удаления целого ресурса через tombstone, hunk coordinates и игровой верификации. Отсутствие файла в моде означает «мод его не заменяет», а не удаление из vanilla. См. [ADR-0006](adr/0006-read-only-first-slice.md).

## 7. Ограничения и safety nets

1. `git merge-file` может вернуть формально «clean» файл со сломанной логикой. Нужны семантические и игровые тесты.
2. Плохой baseline делает даже корректный алгоритм неверным. Проверка базы — жёсткий precondition.
3. Нельзя просматривать сами моды как Git-репозитории: у модов обычно нет общей VCS-истории. Их общий предок — игровой файл.
4. Ручные resolutions не могут повторно использоваться при изменении любого исходного SHA-256 без повторной проверки.
5. Текстовые конфликты нельзя обнаруживать поиском `<<<<<<<` в сыром коде до обработки (такие последовательности допустимы в строках); ориентироваться на статус инструмента и структурированный план, а перед упаковкой — дополнительная проверка маркеров в известных конфликтных файлах.
