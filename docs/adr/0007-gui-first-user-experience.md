# ADR-0007: Графический MVP без консольных действий пользователя

- **Статус:** Accepted
- **Дата:** 2026-10-26
- **Уточняет:** ADR-0001, ADR-0005; ADR-0006 остаётся описанием технического среза

## Контекст

Владелец требует простой UX/UI для обычных игроков: никаких консольных команд в пользовательском сценарии. Ранее CLI считалась MVP, GUI — P2. Такой результат не обеспечивает нужный опыт даже при корректном merge-ядре. Наличие технического CLI не равно готовому продукту.

## Решение

1. Графическое офлайн-приложение Windows/macOS — обязательный P0 первой пользовательской версии. Не откладывать базовый GUI до AST/XML-aware merge. Основной сценарий: открыть → выбрать игру/моды → проверить → создать отдельный мод → открыть папку/инструкцию включения.
2. Для игрока нет обязательного терминала, консольного окна, команд, ручного Python/Git/Lua/PATH, конфигов или baseline manifest. Готовая поставка включает проверенные runtime и инструменты для каждой ОС/архитектуры. Компоненты/хеши проверяются внутри; отсутствующая база или инструмент блокируют операцию, не упрощают safety.
3. CLI остаётся только developer/CI adapter; не удалять и не ломать существующие тесты. GUI обращается к прикладному сервису/структурированным результатам ядра, не требует, чтобы пользователь запускал CLI или разбирал JSON/stdout. Конкретный toolkit и способ упаковки выбираются отдельным проверяемым implementation spike, не назначаются документацией без пробы.
4. Длинные операции выполняются вне UI thread, имеют прогресс и безопасную отмену. Единый BuildPlan и проверка входных хешей не позволяют собирать по устаревшей проверке. Технические детали отделены от понятного резюме и конкретных действий.
5. Fail-closed, read-only исходники, отсутствие last-mod-wins, запрет DLL/неверной базы и отдельный managed output сохраняются. Активная кнопка создания зависит от engine/installable gates, а не оформления экрана. Активация модов в игре остаётся ручной штатной операцией, без редактирования mods.xml.
6. Обязательны UI/e2e и clean-machine проверки готовой поставки на обеих ОС без developer tools, доступность и наблюдаемый usability walkthrough с обычным пользователем. CLI goldens и наличие workflow не заменяют эти gates.
7. Пользовательский README не предлагает команды как способ пользования приложением. Технические инструкции остаются в CONTRIBUTING и внутренних контрактах. GUI пока не реализован; изменение требований не объявляется выпуском приложения.

## Последствия

+ Существующее merge-ядро сохраняется и получает понятную пользовательскую оболочку.
+ Установка, диагностика, конфликты и восстановление входят в UX, а не перекладываются на игрока.
- P0 включает разработку GUI, фоновых операций, упаковку runtime/backend/validator, лицензии поставки и платформенные проверки.
- CLI-прототип и полный M1 engine недостаточны для пользовательского MVP; M2 завершается только вместе с GUI и проверенной поставкой.

## Проверки и связи

Локальный packaging spike 2026-10-29: существующее tkinter-окно собрано PyInstaller 6.22.3 на Windows 10 x64 / Python 3.14.0. Проверены packaged JSON schema/исходники для engine hash, запуск из другого каталога без developer tools в PATH и штатное закрытие окна. Это ограниченное доказательство упаковки окна: выбор окончательного кроссплатформенного toolkit/поставки, встроенные Git/Lua, clean-machine, accessibility, UX/e2e и игровые gates остаются открытыми. JSON-контракт и правила merge этой задачей не изменяются.
